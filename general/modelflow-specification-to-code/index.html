ModelFlow: From Model Specification to Executable Code

Summary¶

ModelFlow uses a deliberately lightweight and layered architecture for specifying, expanding, normalizing and translating economic models into executable code.

The central principle is:

Use Python syntax wherever possible, transform only the notation specific to economic modelling, and delegate the general language machinery to Python and its scientific ecosystem.

This chapter follows the translation side of the architecture: the ModelFlow DSL and imported model formats, dimensional expansion, normalization, tags and generated variants, AST validation, token rewriting, and execution as Python or Numba-compiled code. It also sets out what the DSL deliberately leaves out, because the user interface around the equations is Python itself. The next chapter, Model structure and solution, starts from the executable equation system and explains graph ordering, Gauss-Seidel and Newton solution. Local stability and model dynamics then uses the derivative machinery for stability analysis.

The historical development that preceded ModelFlow—MACRO/NASS and PCIM—is described separately in Historical background.

An algebraic modeling language for root finding¶

For a reader who knows GAMS, AMPL or Pyomo, the shortest description of what follows is that ModelFlow is an algebraic modeling language, pointed at a different problem class.

The family traits are all here: declarative algebraic notation for the equations; sets and indexed expansion, so that one written relationship becomes many concrete ones; specification kept separate from the data and from the solver; derivatives generated by the system rather than supplied by the modeller; and several solvers selectable against the same unchanged specification.

What differs is what is being solved. An algebraic modeling language is normally aimed at optimization — an objective subject to constraints. ModelFlow is aimed at a square system with no objective: as many equations as endogenous variables, solved for the values that make them hold simultaneously. In GAMS’s own vocabulary that is a CNS, a constrained nonlinear system, rather than an LP or an NLP. Root finding is therefore not an implementation detail; it is the model class the language exists to express. Two later sections read more easily with that in mind: Normalization rearranges each equation so that one variable stands alone on the left, which is the form fixed-point iteration can use directly, and Exogenization swaps which variables are unknown and which are given — in a square system, simply a different choice of what to solve for.

Two things set ModelFlow apart from the mainstream of that family. Time is first-class rather than modelled as a set: lags and leads are notation, and the solution runs recursively over periods, stacked only where leads require it — which is what the ordering and decomposition in Model structure and solution exist to exploit. And ModelFlow generates and executes its own code rather than emitting an instance for a third-party solver, delegating the linear algebra to SciPy but not the nonlinear solution. In that second respect it resembles Dynare, which likewise generates code; the comparison is drawn in Historical background.

Why the language can be smaller¶

The narrower target is what makes the smaller language possible.

A general algebraic modeling language has to serve linear programs, nonlinear programs, complementarity problems and mixed-integer models, in any application domain, and its notation has to be general enough to carry all of that. ModelFlow aims at one class: time series models, in which the data is indexed by period and the equations say how the variables move from one period to the next.

Econometric models are the origin of that class and still the main case — macroeconomic models, stress-test models, projection models — but the class is wider than econometrics and ModelFlow is not restricted to it. Anything that is a system of difference equations in discrete time has the same shape and is handled the same way: epidemiological contagion models, demographic and cohort projections, general time-oriented difference systems, and differential systems written in discretized form. What these share is not their subject matter. It is that a period’s state is a function of earlier periods, which is exactly what the notation and the solvers are built around.

Narrowing the target means the specification can be simplified rather than generalized. Sets exist because models are disaggregated by sector, age or country, not because a general index mechanism is wanted for its own sake. Time needs no set at all, because there is only ever one time dimension. The declarations that a general language requires — variable types, domains, model membership — mostly follow from the equations themselves and can be inferred. What is left on the page is close to the algebra an economist would write anyway, which is the whole point: a specification that stays parsimonious and stays readable as economics.

Drud (1983) drew the same boundary, for the same reason. Surveying sixteen modelling systems, he selected them on exactly this criterion — only systems based on time series models — because that is what makes such systems comparable at all. The ones he compared are the ancestors of the ones ModelFlow is compared with here: TSP, TROLL, MODELEASY, SAS/ETS, XSIM.

His paper is also an early and unusually clear statement of a trade-off that recurs throughout this chapter. Drud classifies the equation formats a modelling system will accept as var = expr, f(var) = expr with invertible f, expr = 0, and the fully general expr1 = expr2. The choice is not independent of the solution algorithm. Gauss-Seidel needs a variable standing alone on the left, so it needs one of the first two forms; Newton and minimization methods take the general ones. A system that accepts general equations and wants to use Gauss-Seidel must therefore normalize them, and the normalization is not part of the model — it is information the algorithm needs and the model does not carry. That is exactly what the Normalization section below does, four decades later, and the reason it is a separate stage rather than something the modeller is asked to supply.

Python is the user interface¶

The DSL described in this chapter covers one thing: the equations. Everything around them — reading data, constructing scenarios, driving runs, inspecting results, producing charts and tables — is done in Python, against the model object, in a language ModelFlow did not have to design.

This is the second half of the narrowing argument above.

A self-contained modelling system has to grow its own everything. The systems in Drud’s survey each acquired a command language, then a data-management layer, then loops and conditionals, then a table and reporting facility, then graphics, then some way of calling out to code the system could not express. None of that is modelling. It is general-purpose programming, arrived at one requirement at a time, and every system’s version of it has to be separately designed, documented, maintained and learned.

ModelFlow does none of it. The specification language stops at the equation, and the work surrounding it is ordinary Python:

  • Data wrangling is pandas. A model’s data is a DataFrame, so joins, resampling, interpolation, and reading from Excel, SQL, Parquet or a web API are all available without ModelFlow implementing any of them.

  • Control structures are Python’s. A scenario sweep is a for loop, a conditional run is an if, a family of variants is a list comprehension. There is no ModelFlow macro language, because there is nothing left for one to do.

  • Updating and scenario construction are assignment and arithmetic on the data, written in the same notation as the rest of the analysis.

  • Reporting and visualization are matplotlib, plotly and the notebook. ModelFlow adds model-aware convenience on top — a variable charted across scenarios, an attribution table — but these are thin layers over the standard libraries, not a report-writing language of their own.

The gain is not only access to the ecosystem, considerable though that is: statistical libraries, optimizers, machine-learning tools, testing frameworks, version control, and a language most quantitative analysts already know. The gain is equally in what never had to be built. Each of those facilities is a subsystem ModelFlow did not design, does not document and cannot break, which is a large part of why the framework is as small as it is.

The division is clean. ModelFlow supplies what is specific to models: equations, expansion, normalization, ordering, solvers, attribution. Python supplies what is general. That is the same boundary that runs through the rest of this chapter, applied to the user’s side of the system rather than the compiler’s — transform only what is specific to economic modelling, and delegate everything else.

Pyomo, one of the algebraic modeling languages named earlier, is embedded in Python for the same reason, which suggests the trade is not peculiar to this problem class.

The ModelFlow equation DSL¶

A ModelFlow model is written as economic equations rather than as low-level Python array operations.

A simplified equation might be:

FRML <> Y = C + I + 0.8 * Y(-1) $

The expression

C + I + 0.8 * Y(-1)

is deliberately close to legal Python syntax.

Normal arithmetic, parentheses, operator precedence, function calls and nested expressions can therefore be delegated to Python. ModelFlow mainly has to understand constructs that have a special model meaning.

For example:

Y(-1)

is syntactically a legal Python function call, but ModelFlow interprets it as variable Y lagged one period.

This allows ModelFlow to avoid implementing a complete expression language of its own.

Where the notation comes from¶

The notation is inherited rather than invented. FRML is TSP’s keyword for a formula, and TSP is where it reaches ModelFlow from: the ADAM equations that the first generation of this architecture translated were TSP equations, as described in Historical background.

TSP is old enough to be an ancestor of most of the field. Development began at MIT in 1965–1966 and continued at Berkeley, under Robert E. Hall, and by the time of Drud’s survey it was running at over five hundred sites, among the most widely installed systems there. Its descendants are in use today: MicroTSP, written by David Lilien and first released in 1981, was rewritten for Windows and released as EViews in 1994 Renfro, 2004.

The family resemblance is easy to see, and it runs wider than one lineage. A behavioural equation in EViews, in Dynare’s .mod notation, in WinSolve and in the ModelFlow DSL is the same line of algebra with a different keyword in front of it and a different convention for writing a lag. That is not imitation. It is what a notation converges on once the target is fixed as time series models and the aim is to keep the specification close to the economics. It is also what makes the preprocessors described further down tractable: the equation bodies largely carry over, and the work is in the conventions surrounding them.

Individual equations like this one are, however, rarely written by hand in large models. They are usually produced — by the higher-level DSL, by an import preprocessor, or by normalization, each taken up in the sections that follow. Validation and token rewriting, further down the chain, operate on the equations that those earlier stages generate.

Higher-level model specification DSL¶

Large models often contain many equations that have the same economic structure but differ across dimensions such as sectors, ages, commodities, countries or sexes. Writing every expanded equation separately would be verbose and could hide the economic structure.

ModelFlow therefore has a higher-level specification DSL with constructs including lists, do, doable, sum and tags.

A list defines a model dimension. Each statement is terminated by $:

list ages  = ages  : age_0 * age_101 $
list sexes = sexes : female , male   $

The * in age_0 * age_101 is a range operator: a common alphabetic prefix followed by a numeric range expands to the whole sequence AGE_0, AGE_1, ... AGE_101.

A single list statement can also define several parallel sublists, separated by /. The sublists are aligned element by element, so one loop can substitute matching values from each:

list banklist = bank    : Danske , Nordea , Jyske /
                country : DK     , SE     , DK    $

An equation can then describe an entire family of equations:

doable POP_PRIMO__{SEXES}__{AGES}
    = POP__{SEXES}__{AGES_BEFORE}(-1) $

Summation can also be expressed directly at the model-specification level:

FRML <> MIGRATION__TOTAL =
    SUM(AGES, SUM(SEXES, MIGRATION__{SEXES}__{AGES})) $

The higher-level DSL is not merely shorthand. It expresses the dimensional and structural logic of the model more directly. The two levels are distinct in purpose: the higher-level DSL expresses dimensions, repeated structures, sums, tags and model transformations, while the equation DSL of the previous section expresses individual economic equations in Python-compatible notation. Expansion turns the first into the second.

Preprocessors and models from other systems¶

A model does not have to originate in the ModelFlow DSL. Source-specific preprocessors translate models from other modelling systems into the common ModelFlow representation.

Read the table as a list of models that have been onboarded, not as a claim of compatibility. The preprocessors are not reimplementations of EViews, Dynare, GAMS or Excel. They do not attempt to cover everything those systems can express. Each was written to bring in a particular model, and handles the constructs that model actually uses.

SourceModulePreprocessor responsibility
EViewsmodelgrabwf2.pyRead .wf1/.wf2 workfiles; translate equations, data and metadata
World Bank macro modelsmodelmacrograb.pyTranslate the specification through modelnormalize
Dynaremodel_dynare.pyRead expanded .mod output; map syntax and timing conventions
GAMS / GDXmodelgrabgdx.pyRead GDX files via gams.transfer; extract time-indexed variables and scenarios
Excelmodel_Excel.pyInterpret workbook-based model specifications

Not every import has to become a library module. A model that is translated once, rather than repeatedly, can perfectly well be handled by a one-off script whose output is a finished ModelFlow model. The FRB/US model is the notable example: the Federal Reserve distributes its equations in XML, and the translation was done as a separate exercise, leaving behind a stored model that the example notebooks simply load. Only sources that are imported often enough to be worth generalizing earn a place in the table above.

Either way the effect is the same, and it is the point of the arrangement: source-specific knowledge is separated from the downstream model machinery. The source system holds the original specification; the preprocessor understands its syntax and conventions; the ModelFlow representation provides a common equation and model form; and the ModelFlow runtime provides common solving, simulation, analysis and reporting.

Once translated, models from different sources can use the same ModelFlow facilities for solving, scenarios, attribution, visualization and reporting.

Onboarding a model, not supporting a system¶

This is a deliberate choice about scope. The alternative is a trap.

General compatibility means committing to the whole of another system’s semantics. Every option, every estimation command, every corner of its syntax. Most of it no particular model uses. The obligation is unbounded, and it grows with every release of the other system.

Onboarding starts from the other end. The question is not “what can EViews express?” but “what does this model need?” That has a finite answer.

It can also be checked. The imported model is solved, and its results compared against the original system’s — equation by equation where necessary. A model that reproduces its source is onboarded, whatever fraction of the source language was involved.

The practical consequences are worth stating plainly:

  • A model from a listed source is not guaranteed to import. It may use constructs no earlier model needed.

  • The gap is then usually one specific construct. Extending the preprocessor to cover it is a bounded task.

  • Coverage grows model by model, driven by demand rather than by the source system’s feature list.

The offer is not “run your EViews models in Python”. It is that an onboarded model gains the whole ModelFlow apparatus — graph analysis, attribution, the solvers, the reporting — whatever notation it was written in.

Normalization¶

Expanded equations are not yet in a form that can be evaluated. An equation may have an expression on the left-hand side, it may be implicit, and it may use economic transformation functions that have no Python equivalent.

Normalization (modelnormalize.py) closes this gap. It transforms

g(y,x)=f(y,x)⟹y=F(x,z)g(y, x) = f(y, x) \quad\Longrightarrow\quad y = F(x, z)g(y,x)=f(y,x)⟹y=F(x,z)
(1)

so that each equation assigns exactly one endogenous variable. This is the step that makes the rest of the chain possible: the graph analysis needs a single left-hand-side variable per equation to define its nodes, and Gauss-Seidel needs an assignment it can evaluate.

Normalization has three parts.

Preprocessing of economic functions¶

Transformation functions familiar from econometric practice are expanded into elementary arithmetic before anything else happens:

WrittenExpanded to
DIFF(X)((X)-(X(-1)))
DLOG(X)DIFF(LOG(X)), then expanded again
PCT(X)(100 * ((X) / (X(-1)) - 1))
PCY(X)as PCT, but against X(-4)
MOVAVG(X, n)((X + X(-1) + ... )/n.0)
LOGIT(X)(LOG(X/(1.0 - X)))

D(...) is accepted as an alias for DIFF(...). A separate step, fixleads, rewrites a lead written as X(1) into the canonical X(+1) so that leads and lags are distinguishable later.

Symbolic isolation of the endogenous variable¶

Most equations need no isolation at all. If the left-hand side is already a single variable — the ordinary case Y = f(X) — the equation is used as it stands, and no symbolic algebra is invoked.

Applying one of the preprocessing functions above to the endogenous variable itself does not change that in substance. DIFF(Y) = f(X) unfolds to (Y) - (Y(-1)) = f(X), and isolating Y is just moving Y(-1) across the equals sign; DLOG(Y) = f(X) unfolds to a difference of logs, and isolating Y is the same move. Each of these transformation functions has one fixed, known inverse, so in general DIFF and DLOG on the left-hand side are handled by shuffling terms, not by solving anything.

Genuine symbolic work is needed only when the left-hand side is not one of these recognized shapes — a hand-written multi-term expression (A - C = B) — or when the modeller asks to normalize for a variable that sits on the right-hand side, where the coefficient or context is not fixed in advance. Lagged terms are first pasted into atomic symbols (X(-1) becomes a single name ending in ___LAG) so that SymPy treats them as constants rather than as function calls, and the result is unpasted afterwards. LOG and EXP are lowercased to match SymPy’s names, and a clash dictionary maps every model variable to an explicit symbol so that names such as E, I, S or beta are not silently reinterpreted as SymPy built-ins.

Equations that are genuinely implicit are handled differently: instead of being solved, they are turned into a residual equation

Y___RES = ( rhs ) - ( lhs )

which the Newton solvers can use directly. Model structure and solution explains why the distinction between a normalized row and a ___RES row matters for the Jacobian.

That some equations resist normalization is a known feature of econometric models rather than an awkwardness of this implementation. Don (1990) makes the point that a good normalization does not always exist — even where a bad one does — and treats the handling of implicit equations, whether individually noninvertible equations or system equilibrium conditions, as a problem to be solved rather than avoided. The residual form is how that is done here.

Generation of equation variants¶

The operational variants described in the next section are not produced by symbolic algebra. They are textual constructions — the add-factor term is appended, the exogenization switch is wrapped around the right-hand side, and the reverse equation is written directly. For an equation whose left-hand side is already a single variable, the whole set is assembled by string composition:

normalized    Y = (f(X) + Y_A)
fixable       Y = (f(X) + Y_A) * (1-Y_D) + Y_X * Y_D
add factor    Y_A = (Y) - (f(X))
fitted        Y_FITTED = f(X)

This is worth stating plainly because it is what makes the variants cheap and predictable. No equation is re-derived, nothing depends on SymPy succeeding, and the generated forms are recognizably the modeller’s own right-hand side.

Where isolation is needed at all, the same shuffling continues to cover it. For DIFF(Y) = f(X) with an add factor requested, the add-factor term is inserted before the equation is rearranged, and both variants fall out of the same move: Y = Y(-1) + f(X) + Y_A, and Y_A = (Y) - (Y(-1)) - f(X). Nothing here needs more than moving terms across the equals sign — only the hand-written or right-hand-side-variable cases mentioned above call for SymPy to do work beyond that.

Normalization therefore emits, from one authoritative specification:

  • the normalized equation, optionally with an add factor appended;

  • the add-factor equation, for the reverse calculation;

  • a fixable form, which embeds the exogenization switch;

  • a fitted form, without add factor or exogenization, useful for estimation and for tracking historical fit.

Tags and generated model transformations¶

Tags allow information about how an equation should be treated to accompany the economic equation without putting operational details into the mathematical expression itself. Preprocessing uses them to select which of the normalization variants are generated for a given equation.

Important applications include add factors, exogenization, reverse calculation of add factors, and other model-specific transformations.

Add factors¶

Consider the authoritative economic equation:

Y = f(X)

For simulation, preprocessing can generate an equation with an add factor:

Y = f(X) + Y_A

The add factor allows the equation to reproduce a historical value, baseline path, judgemental adjustment or imposed scenario while retaining the underlying behavioural relationship. The suffix is configurable; _A is the default.

Exogenization¶

Normally Y is endogenous: the model calculates it. For some simulations, however, the modeller may want to impose a path for Y. The variable is then exogenized.

ModelFlow implements this without a second model. A fixable equation carries the switch in the equation itself:

Y = (f(X) + Y_A) * (1 - Y_D) + Y_X * Y_D

Y_D is a dummy: where it is 0 the equation behaves normally, and where it is 1 the value of Y is taken from the exogenous series Y_X. Exogenization therefore becomes a matter of setting data, and it can differ from period to period without regenerating the model.

Reverse calculation of add factors¶

If Y is given, the same economic relationship can be reversed to calculate the add factor required to make the equation hold:

Y_A = Y - f(X)

As described under normalization, this equation is not written separately by the modeller: it is generated alongside the normalized one, in the ordinary case simply as Y_A = (Y) - (f(X)). ModelFlow can collect these equations into a separate reverse model.

Model variantGivenCalculatedEquation
Normal simulationY_A and explanatory variablesEndogenous YY = f(X) + Y_A
Reverse/add-factor modelExogenized Y and explanatory variablesRequired Y_AY_A = Y - f(X)

This is useful when constructing a baseline or imposing a scenario path. The modeller can:

  1. exogenize selected variables;

  2. provide their desired paths;

  3. run the reverse model;

  4. calculate the required add factors;

  5. return to the normal model with those add factors.

The normal and reverse models are generated from the same authoritative economic specification, so no hand-written second version of the model has to be maintained.

Validate before rewriting¶

Syntax checking is performed before ModelFlow rewrites model tokens into implementation-level Python.

Python’s ast module can be used because the expression part of the ModelFlow DSL is intentionally Python-compatible:

import ast

ast.parse(expression)

The AST is used here for validation and error localization, not as the main transformation mechanism.

Suppose a modeller writes:

Y = C + (I * + 0.8 * Y(-1)

Because syntax validation occurs before rewriting, ModelFlow can point to the error in the original economic equation. The checker parses the expression exactly as written — without stripping blanks or newlines — precisely so that the line and column numbers reported by Python refer to the modeller’s own text. It then reproduces the offending line with a caret under the reported column:

Syntax error at line 1, column 19: '(' was never closed
Y = C + (I * + 0.8 * Y(-1)
                  ^

If variables had already been transformed into internal array references and indices, the syntax error could instead point into generated Python source that the modeller never wrote.

Thus Python’s AST acts as a front-end syntax checker for the ModelFlow DSL.

Regex and token rewriting¶

After syntax validation, ModelFlow performs its domain-specific substitutions.

Regular expressions are appropriate because they are not used to parse the complete expression grammar. They identify only constructs for which ModelFlow has a special interpretation.

To see what the substitution produces, it helps to know what the model runs on. A ModelFlow model holds its data in a pandas DataFrame with periods as rows and variables as columns. For solving, that DataFrame is handed over as a plain two-dimensional NumPy array, values. Every model variable therefore has a fixed column number, and the current period is a row number, row.

A lag or lead is then nothing more than an offset on the row index. If Y happens to be column 42:

Y        ->  values[row,   42]
Y(-1)    ->  values[row-1, 42]
Y(+1)    ->  values[row+1, 42]

The transformation is therefore mainly:

model token -> implementation token

Python remains responsible for the surrounding expression. This is also why lags are essentially free: no shifting or copying of series takes place during solving, only integer arithmetic on a row index.

Why the NumPy array rather than the DataFrame¶

Nothing forces this choice. The generated code could just as well address the DataFrame directly by label, which would be far more readable:

df.loc[period, 'Y'] = df.loc[period, 'C'] + df.loc[period, 'I'] + 0.8 * df.loc[prev_period, 'Y']

The problem is when the names are resolved. Every one of those labels has to be looked up in the index and in the column index — a hash lookup, a check, and the construction of a scalar object — and pandas does that work on every single access, every time the line is executed. A model equation is not executed once: it is executed for every iteration, of every period, of every scenario. In a model of a few thousand equations solved over a few hundred periods, that is easily hundreds of millions of label lookups, all of them re-deriving an answer that never changes.

Translating the names into positions moves that work to transpile time. Y is looked up once, while the source is being generated, and the answer — column 42 — is baked into the generated text as an integer constant. At solve time nothing is resolved at all:

Label access on the DataFramePosition access on the array
Y resolved to a locationOn every evaluationOnce, when the code is generated
Cost per accessHash lookup, bounds check, scalar boxingPointer arithmetic on a float array
What varies at solve timeThe name (constant) and the periodOnly row, an integer

The saving is large — this is one of the main reasons ModelFlow can solve realistically sized models at acceptable speed — and it comes at no cost in expressiveness, since the modeller never sees the generated code anyway. The DataFrame is not abandoned: it remains the model’s data structure, and results are handed back as a DataFrame. It is simply stepped out of for the duration of the solve, via .values, which exposes the underlying block of floats without copying it.

There is a second consequence, taken up in the next section. A two-dimensional array of floats is exactly the kind of object Numba can compile; a pandas DataFrame is not. Resolving names to positions is therefore also what makes the just-in-time path possible at all.

A variant: the stuffed solution vector¶

Position access can in principle be taken one step further. Rather than indexing into the full two-dimensional array, a solver can gather the values a period actually needs — the current value of each variable, and those lags the equations really use — into a single compact one-dimensional vector, iterate on that, and write only the endogenous results back afterwards. Each variable and lag then has a fixed offset in that vector, and the whole working set is contiguous in memory.

ModelFlow has one Gauss-Seidel solver built this way, but it is an experiment rather than the normal path: the ordinary solvers address the two-dimensional array directly, as above. The idea is older than ModelFlow — it comes from PCIM, where it was a necessity rather than an option, and the historical background describes why.

Outsourcing the language chain to Python¶

After ModelFlow-specific substitutions, the result is legal Python source.

Python handles constructs such as:

A + B * C
(A + B) * C
A ** B
func(A, B)
-A
A / (B + C)

ModelFlow therefore does not have to duplicate Python’s rules for precedence, associativity, parentheses, numeric literals, function calls, unary operators, or nested expressions.

This strategy is not peculiar to ModelFlow. Generating code in a general-purpose language and letting its compiler do the rest is a well-established way of building modelling systems: Dynare translates its .mod specifications into MATLAB/Octave, and the approach goes back at least to the mainframe era. Only the source notation and the target language differ; the historical background discusses the parallel.

The generated source is text, so it can simply be compiled and executed:

code = compile(generated_source, filename, "exec")
exec(code, namespace)

The equations of the model become the body of a generated function, and solving the model means calling that function repeatedly.

Just-in-time compilation¶

Because the output is source text rather than an in-memory data structure, ModelFlow gets a second compiler for free. With the ljit option, the same generator emits the same equations decorated for Numba:

from numba import jit

@jit("(f8[:,:],f8[:,:],i8,f8)", fastmath=True, nopython=True)
def los(values, outvalues, row, alfa):
    ...

The explicit signature — two float arrays, an integer row and a float damping factor — lets Numba compile ahead of the first call instead of specializing on the first argument types it sees.

That signature is only writable because of the decision described under token rewriting. Numba’s nopython mode compiles a restricted set of types, and a two-dimensional array of floats indexed by integers is squarely within it, while a pandas DataFrame indexed by labels is not. Having already resolved every variable name to a column number, the generated equations contain nothing but arithmetic and integer indexing — so the same text that Python can exec can also be handed to Numba and compiled to machine code, with no separate code path for the two cases.

Two practical points follow from the size of real models. First, the equations are emitted in chunks (30 by default) wrapped by a master function, because a single function with many thousands of statements is slow for Numba to compile. Second, the generated source is written to a file under modelsource/ and the compiled functions are cached on the model instance, so the compilation cost is paid once rather than on every solve.

The division of labour is:

LayerResponsibility

Runtime error localization¶

Validating before rewriting keeps syntax errors anchored to the equation the modeller wrote. The same problem arises again at solution time, and for the same reason: the code that fails is generated code. A logarithm of a negative number or a division by zero raises an exception somewhere inside a machine-written function of several thousand lines.

ModelFlow solves this by generating the error handling along with the equations. Each block of generated code is wrapped so that an exception reports the line number at which it occurred:

except:
    errorfunk(values, sys.exc_info()[2].tb_lineno, overhead=..., overeq=...)

Because the generator knows how many lines of preamble it emitted (overhead) and how many equations preceded the current chunk (overeq), the Python line number can be mapped back to a position in the model’s solve order — and therefore to a specific economic equation.

The handler then reports the failing equation, and it snapshots the entire data array as a DataFrame on the model (.errdump, copied to .lastdf) so the modeller can inspect the state of every variable at the moment of failure. It also inspects the failing equation for LOG(...) calls and evaluates their arguments, since a non-positive argument to a logarithm is the single most common cause.

The design principle is the same at both ends of the chain: generated code is an implementation detail, and the modeller should never be asked to debug it.

A worked example: specification to executable code¶

The stages above are easier to see in one equation carried from specification to executable code. Take a consumption function specified over a list of household groups.

Specification. A list defines the dimension, and one doable describes the whole family of equations:

list groups = groups : young , old $

doable  DIFF(C__{GROUPS}) = 0.5 * DIFF(YD__{GROUPS})
                          + 0.3 * (YD__{GROUPS}(-1) - C__{GROUPS}(-1)) $

Expansion. The higher-level DSL produces one equation per group. Following C__YOUNG:

FRML <> DIFF(C__YOUNG) = 0.5 * DIFF(YD__YOUNG)
                       + 0.3 * (YD__YOUNG(-1) - C__YOUNG(-1)) $

Preprocessing. DIFF is expanded into elementary arithmetic:

((C__YOUNG) - (C__YOUNG(-1)))
    = 0.5 * ((YD__YOUNG) - (YD__YOUNG(-1)))
    + 0.3 * (YD__YOUNG(-1) - C__YOUNG(-1))

Normalization. The left-hand side is DIFF(C__YOUNG), one of the recognized shapes, so isolating C__YOUNG is a shuffle: the add-factor term is inserted, and C__YOUNG(-1) is moved across the equals sign:

C__YOUNG = C__YOUNG(-1)
         + 0.5 * ((YD__YOUNG) - (YD__YOUNG(-1)))
         + 0.3 * (YD__YOUNG(-1) - C__YOUNG(-1))
         + C__YOUNG_A

The reverse equation falls out of the same move, this time isolating C__YOUNG_A. Had the specification been written directly as C__YOUNG = ..., with no DIFF on the left, both forms would have been assembled textually in exactly the same way:

C__YOUNG_A = ((C__YOUNG) - (C__YOUNG(-1)))
           - 0.5 * ((YD__YOUNG) - (YD__YOUNG(-1)))
           - 0.3 * (YD__YOUNG(-1) - C__YOUNG(-1))

If the equation is also made fixable, the normalized form is wrapped with the exogenization switch described under tags, ... * (1 - C__YOUNG_D) + C__YOUNG_X * C__YOUNG_D — again assembled textually, not derived.

Validation. The normalized equation is parsed with ast.parse as written. Any syntax error is reported against this text — which the modeller can still recognize — rather than against the array code generated next.

Token rewriting. Each variable becomes a column index and each lag a row offset. If C__YOUNG is column 3, YD__YOUNG column 7 and C__YOUNG_A column 11:

values[row,3] = (values[row-1,3]
                 + 0.5 * ((values[row,7]) - (values[row-1,7]))
                 + 0.3 * (values[row-1,7] - values[row-1,3])
                 + values[row,11])

Execution. This line is one statement in a generated function, compiled with compile/exec — or, with ljit, emitted into a Numba-decorated chunk and compiled to machine code. Gauss-Seidel solves the model by calling that function repeatedly.

The continuation of this example—its graph edge, symbolic derivative and Jacobian row—is given in Model structure and solution.

Layered view of the translation pipeline¶

LayerMain function
External model formatsEViews, Dynare, GAMS/GDX, Excel and other sources
PreprocessorsTranslate source-specific representations into ModelFlow
Higher-level DSLLists, do, doable, sum, tags and dimensional expansion
NormalizationExpand economic functions; isolate the endogenous variable
Generated model variantsAdd factors, exogenization, reverse and fitted equations
Equation DSLCompact Python-compatible economic equations
ValidationPython AST checking against the original equation
TranslationRegex and ModelFlow-specific token substitution
Python toolchainGeneral parsing, compilation and execution
Numba (optional)Machine-code compilation of the generated source
Runtime diagnosticsMap execution errors back to the failing economic equation

The output of this pipeline is an executable system of model equations. The next stage is structural analysis and numerical solution, described in Model structure and solution.
